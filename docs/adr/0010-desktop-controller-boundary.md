# Desktop applications are controller-only integrations

Status: accepted

Desktop applications are integrated as External controllers, never as Members, because letting the user and an Agent interact directly inside a member's desktop client would bypass the Agent Team message model. A desktop host is Desktop-ready only when the same application installation also provides a Bundled execution engine that is usable for framework-owned member turns; a controller-only installation is not a supported desktop surface.

One desktop application registration provisions both halves together. Its user-visible conversation is the Desktop controller session, while its Bundled execution engine runs member turns in framework-owned session storage that is isolated from the user's normal desktop history. Member execution remains available while the desktop window is closed, but Active wake never launches a closed desktop application; it only wakes a session that is already available.

Desktop applications are the daily command surface, while the Agent Team panel remains the observation and administration surface. Closing a desktop conversation or application does not release its team controller seat. Another Desktop controller conversation may inspect the team and request an explicit Controller takeover; the takeover is visible in team history and, when possible, wakes the previous controller so it learns that it is now read-only. Member conversations and execution history remain visible only in Agent Team, never in the host application's normal chat list.

Independent Desktop controller conversations do not see each other's teams by default. Cross-conversation access requires an explicit team identifier or an Agent Team panel takeover entry. Installation and discovery live in the Agent Team interface: it detects supported desktop applications and shows separate controller and execution-engine diagnostics before enabling an application. An application whose diagnostics are incomplete is not enabled. A fully usable application may still be enabled as Pull-only when Active wake is unavailable, with that limitation shown explicitly rather than treated as a connection failure.

Agent Team remains a local single-user product. Multiple Desktop controller conversations are alternative control points for the same user, not separate accounts. Any controller conversation for that user may request a Controller takeover by supplying the exact team identifier; no second approval from the previous controller or the panel is required. The takeover remains auditable, the previous controller stays able to view the team read-only, and every controller that has established a relation to the team remains visible to the user. Multi-user and remote authorization are outside the current product boundary.

Installing a desktop integration and activating a Desktop controller conversation are separate events. A conversation activates only when the user invokes the Agent Team Skill or explicitly asks for Agent Team work; ordinary host chats never become controllers or call Agent Team in the background. First activation identifies the independent controller conversation, its Agent Team data directory, and its current teams. Removing an integration leaves teams, messages, and members intact while making that controller unavailable.

Agent Team is deliberately a cross-product collaboration control plane. Native multi-agent features remain available and outside Agent Team coordination, and users opt into Agent Team by invoking its Skill rather than by disabling the host's own capabilities. When both systems are visible, the Agent Team workflow treats native subagents as outside its team and does not attempt to mirror or control them. Team membership, messages, decisions, task state, and controller ownership remain authoritative in Agent Team; each host's native conversation is only a client-side transcript.

Desktop controllers may create, direct, archive, and restore teams. Permanent deletion remains a human-only action in the first-party Agent Team interface.

Failure never causes an implicit host switch. If a member engine fails, the work stays attributed to that member and fails visibly; the user or active controller must explicitly choose a replacement. If no compatible Bundled execution engine remains, existing teams stay readable and manageable, but new member work is blocked.

Multiple Desktop-ready products may supply the controller and member engines of one team; their installed applications and accounts remain independent. The first supported desktop families are Codex, DSH, and Claude. Additional desktop products wait until this controller-plus-engine model has an established verification and installation path.
