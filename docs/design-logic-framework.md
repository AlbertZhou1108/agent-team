# 设计逻辑框架:元素的描述模型(草案)

本文是设计逻辑架构,回答两个问题:**一个页面元素由哪些方面描述**、**每个方面由谁决定**。它是 [frontend-architecture.md](frontend-architecture.md)(技术架构:代码放哪)的上游 —— 逻辑先于技术,技术层是本文的投影。

状态:经逐条逻辑讨论收敛(样式/排印拆分、材质三层结构与可供性约束、大类内化、材质动效签名、解析顺序、状态图均已定案),作为技术架构与后续打磨(材质等)的决策依据。

## 1. 元素的描述模型

> **一个元素 = 一个语义角色,在某个交互状态下,沿五个方面的取值组合。**

五个方面中四个来自讨论共识(样式/材质/行为/布局),一处拆分、两处新增(见 §2 说明)。

元素有**生命周期**:进入(出现)→ 存在(状态图驻留)→ 转移(状态变化)→ 离开(消失)。生命周期不引入新方面 —— 进入/离开是行为(边的特例),转移引起的空间再分配是布局的职责(谁让位、怎么让)。

**框架边界**:内容与业务语义不在本框架内(框架描述呈现,不描述数据);声音与触感不在 Web 端范围;**整页构图**(视觉重心、节奏)是元素组合后的涌现性质,由 DESIGN.md 的原则约束 —— 框架管元素,原则管构图。完备性主张:任何"用户可感知的呈现变化"都必须能归入五个方面之一 × 某个状态 × 某个决策层级 —— 归不进去即框架缺陷,补框架而不是加特例。

## 2. 五个方面

### 2.1 样式 —— 元素"是什么颜色、什么形状"

语义颜色(背景/前景/强调/危险)、形状(圆角/边框/描边)、图标语言。回答"品牌长什么样"。

- 决策源:全局主题偏好(用户选)→ 角色默认 → 组件消费。
- 技术投影:主题维度(29 token,含 radius)。

### 2.2 排印(阅读)—— 文字"读起来多舒服"【从样式拆出】

正文大小、行距、内容宽度、代码字号。与 2.1 拆开的理由:二者变化频率与决策者不同 —— 样式跟品牌走,排印跟阅读偏好走;换主题不应重置阅读设置。

- 决策源:全局阅读偏好,独立于其它方面。
- 技术投影:阅读维度(--reading-*/--code-size)。

### 2.3 材质 —— 表面是"什么物理质感"

材质是物理隐喻,内部为三层结构:

| 层 | 回答 | 例(玻璃) |
| --- | --- | --- |
| 基材 | 像什么(身份隐喻) | 玻璃:可透、光滑 |
| 工艺 | 什么性格 | 液态(流动高光、诱人触摸)、磨砂(安静退后) |
| 参数 | 多强 | 模糊度、透明度、高光强度、粗糙度、立体感 |

**可供性是约束条件**(Norman:材质暗示可交互性 —— 水泥坚硬不可按,玻璃光滑可触):基材与工艺必须与角色职能一致,"材质 × 角色"取值为三态 —— **允许 / 需适配(如液态工艺在阅读面提不透明度保对比度)/ 禁止(水泥 → 操作面)**。

**大类与内化**:用户只选择材质**大类**(玻璃风 / 水泥风 / 纸感风…),大类对应一份内部规格表 —— 每个角色一行,声明基材 + 工艺 + 校正后的参数(视觉列与运动列,运动见 2.4)。内化的模式是"**保留气质特征,按角色修正功能参数**"(液态工艺用于阅读面:保留高光边缘的气质,提高不透明度保住对比度底线)。用户表达气质,系统保证职能正确;工艺、参数、可供性校正不暴露给用户。现实佐证:Glassmorphism 成熟可行,Neumorphism 因"全界面同材质导致可供性失效"被社区淘汰 —— 可供性约束是有翻车案例的设计法则。

- 决策源:全局材质大类(用户)× 大类规格表(设计系统,含可供性三态判定)。
- 技术投影:材质维度(data-material)+ 表面角色选择器 + 规格规则集。

### 2.4 行为 —— 元素"如何动态地变化"

元素因交互或状态变化产生的动态效果(用户原话:展开、收起、被点击、出现/消失)。行为 = **触发 × 过渡 × 循环**:

- 触发语义:用户交互(点击/悬停/拖拽)| 状态变化(出现/消失/展开/收起/加载/错误)| 时间(定时消失的通知、自动刷新指示)
- 过渡规格:时长、缓动、幅度
- 循环:加载点、脉冲等持续动画

过渡规格是复合解析的结果:

> **最终动效 = 风格档(能量:柔和/灵动)⊗ 材质签名(物理词汇:流动/干脆/弹)⊗ 用途语义(反馈/展开收起/浮层进出)⊕ 减少档(全部压平)**

材质大类自带**运动签名**(规格表的运动列):液态玻璃 = 流动高光与低阻尼回弹;纸 = 干脆、无弹性(物理上纸会折不会颤,弹性被材质否决);水泥 = 沉稳、禁止一切弹性;黏土 = 强弹性(squash & stretch)。风格档设定能量级,材质签名圈定物理词汇表,交集为渲染结果(灵动 + 纸 = 纸所允许的最快动效)。

签名来源为**混合制**:基材物理属性(硬度/弹性/质量/透明度)推导词汇边界(什么允许/禁止),设计师在边界内手调特征动效(如液态玻璃的高光轨迹)。

- 决策源:全局动效风格档(用户)× 材质签名(内化)× 用途语义。
- 技术投影:动效维度(data-motion)与材质维度(data-material)联合解析 + 动效契约。

### 2.5 布局 —— 元素与元素"怎么排"

四个子问题:

- **密度**:间距、行高、容器留白 —— 松散/紧凑(用户原话)。格式塔邻近性原则给出它的语义:**密度是"信息分组强度"的旋钮** —— 紧凑 = 声明同组,松散 = 组间边界
- **遮挡**:谁在上谁在下(浮层层次、粘性侧栏)
- **滚动归属**:长内容在哪滚、几层嵌套
- **关系声明**:包含(嵌套)、分组、对等(序列)、关联(标签↔字段)—— 元素间关系由布局表达

- 决策源:全局密度偏好 × 结构骨架。
- 技术投影:密度维度(--density-*)+ 结构骨架类 + z-index 刻度。

## 3. 状态与行为:交互状态图【新增,定案】

状态与行为不是两个并列概念,而是合起来构成元素的**交互状态图**:

- **状态 = 图的节点**:每个状态有五方面的完整解析值
- **行为 = 图的边**:由事件(用户交互 / 数据变化)触发,把元素从状态 A 转移到状态 B
- **动画 = 边的渲染**:从 A 的方面值过渡到 B 的方面值

语义状态全集:默认、悬停、焦点、选中、禁用、加载、错误、待确认。规则:每个角色的每个状态都有五方面描述;状态表达不得只依赖一个方面(颜色不承载唯一信息)。

**状态描述采用差量制**:默认状态持有一份完整描述,其余状态只记录与默认的差异(悬停 = 默认 + 底色叠加,而非第二份完整描述)。这使完备性规则在实践上可执行,也是"状态层令牌"的逻辑基础。

**转移终点不变式**:行为必须把元素精确渲染到目标状态的解析值 —— 途中允许装饰性过冲,但终点不得落在过冲值上(瞬态滚动条 bug 即违反此条:终点落在了测量过冲值上)。

**编舞**:转移改变元素尺寸/位置时(展开把下方内容推下),受影响邻元素是同一编舞的参与者 —— 谁让位、让多少、什么次序,必须可解释而非副作用;多元素交错动画(stagger)同理属编舞。

- 技术投影:语义状态表(DESIGN.md 验收表);状态层令牌(悬停 = 表面色 + 标准透明度叠加,而非独立色值);转移终点不变式已由折叠的 grid-rows 方案落实(逐帧解析,终点即真实布局值)。

## 4. 角色 —— 描述的索引【新增】

描述一个元素的第一句话是它的**角色**:导航面板、上下文面板、会话操作区、**输入面**(文本输入与表单控件 —— 玻璃面板上的输入区需要独立角色保证聚焦可读)、阅读面、浮层、媒体浮层。角色是五个方面取值的默认载体 —— 换角色 = 换一整套默认描述;材质/密度等维度的"作用范围"也以角色为界。

- 技术投影:表面角色体系(角色类 + 属性选择器)。

## 5. 决策层级 —— 每个方面由谁决定

| 层级 | 决定什么 | 例 |
| --- | --- | --- |
| 全局偏好(用户) | 五个方面的风格取向 | 深色 + 松林 + 玻璃 + 柔和 + 标准 |
| 角色默认(设计系统) | 每个角色在每个方面上的适配 | 玻璃在阅读面降级实色;浮层不做透明 |
| 组件实现(业务) | 用什么角色、放什么内容、业务差异 | 成员行用 Item;错误就近用 Alert |
| 实例(页面) | 极少数真实业务差异 | 拖拽把手必须可见 |

决策空间正交,解析空间有向:用户的五个维度选择互不干扰,但系统解析按依赖链执行 —— 明暗 → 主题 → 密度 → 排印 → **材质(规格表)→ 行为(风格档 × 材质签名)** → 输出。层间作用关系(材质影响可读性、布局尺度影响动效时长感知等)由解析链上的适配规则显式管理;分层的价值不是"层间无关",而是把耦合从隐式的意外变成显式的、有方向的规则。

解析链的第 0 步是**环境与能力约束**:设备能力(是否支持模糊)、系统辅助模式(强制对比色、降低透明度)、视口尺寸。它们不是用户的选择,却逻辑上高于用户偏好 —— 强制对比色模式覆盖一切视觉决策。同时澄清:链上的顺序针对**决策值**(偏好与令牌)的解析;布局几何是浏览器对全部决策值的连续计算(排印变化引起内容高度变化,是决策值落地的结果,不是新的解析环节)。

**自洽闭环**:事件(交互 / 数据变化)→ 状态转移(状态图)→ 目标状态的五方面解析(沿决策层级)→ 行为渲染转移(过渡规格 × 编舞)→ 稳定于目标值。任何界面变化都应能完整走通这个环而不缺环节 —— 缺任何一环即是框架或实现缺陷。

规则:下层只能在**不违反上层**的前提下做业务差异;组件层零视觉决策。

## 6. 可靠性规则(框架自检)

1. **归属完备**:任何视觉变化必须能归入"一个方面 × 一个决策层级";归不进去 = 框架缺陷,补框架而不是加特例。
2. **决策正交,解析有向**:用户的维度选择互不干扰;任意(角色 × 方面 × 状态 × 偏好)组合经显式解析链得到唯一确定结果(依赖序:明暗 → 主题 → 密度 → 排印 → 材质 → 行为;适配规则显式化,如"材质 × 角色"三态矩阵)。
3. **状态完备**:每个角色的每个语义状态都有五方面描述。
4. **偏好不被评价**:偏好是主观选择,无对错可言,组合亦无禁忌(特大字号 × 全宽行宽由用户自主取舍);系统不评判组合,只承担实现义务 —— 每一种偏好组合都渲染到客观底线之上(对比度达标、不裁切、不重叠、可交互暗示正确)。"材质 × 角色"的补偿属于这条实现义务,不是对偏好的修正。
5. **用户维度即契约**:组件对维度无感知;维度落地必须伴随可感知的表面消费(样例卡 + 真实表面同步)。
6. **转移终点不变式**:行为必须把元素精确渲染到目标状态的解析值;装饰性过冲允许,但终点不得落在过冲值上。
7. **编舞显式化**:转移引起的空间再分配(邻元素让位)是转移的一部分,谁动、动多少、什么次序必须可解释,不允许作为副作用发生。

## 8. 由框架推出的下一步(供决策)

1. **建成玻璃大类的规格表**(每角色的基材/工艺/参数 + 运动签名列)—— 材质维度打磨的前提;纸感、水泥等未来大类即规格表新行。
2. **状态层令牌** —— 状态描述进契约(悬停/按压 = 表面色 + 标准透明度叠加)。
3. **角色强制化** —— 新表面必须挂角色类,架构文档已列规则,可加检查。
4. **角色状态图文档化**(可选)—— 每个角色一页"状态与转移清单"作为行为用途依据;是否引入状态机库由实践决定。

## 9. 治理 —— 框架自身的扩展规则

框架(本文与架构文档)是唯一事实来源;任何新增、修改、废弃都必须走下表流程并在文档留痕,禁止代码先于文档出现。

| 扩展 | 门槛(全部满足) | 流程 |
| --- | --- | --- |
| 新增角色 | 归位测试失败(现有角色无法描述其职能);有独立的可供性需求;将获得至少两个方面的差异化渲染 | 提案 → 归位测试 → 收敛登记(角色清单 + 规格表加列)→ 实现 → 可感知性验收 |
| 新增材质大类 | 提供现有大类无法表达的气质;承担整张规格表的成本(每角色基材/工艺/参数 + 运动签名);可供性逐格三态判定 | 提案(气质描述 + 物理参数)→ 词汇边界推导 → 手调特征动效 → 规格表成文 → 实现 → 验收 |
| 新增动效风格档 / 密度档 / 阅读档 | 现有档位无法表达;全部消费面经契约变量自动跟随 | 重映射定义 → 文档登记 → 验证 |
| 新增状态 | 现有语义状态无法表达;定义差量来源(从哪个状态派生);可访问性规则同步 | 同上 |
| 新增方面(最高级别) | 出现持续的"归位测试失败"证据 | 重新审视全部映射与文档后,按新增角色同规格流程办理 |
| 修改 / 废弃 | 与新增同门槛;废弃必须提供迁移路径 | 禁止并存双套 |

治理主体:用户为最终决策者;ZCode 负责提案、实现与验收记录。偏好本身永不进入治理流程 —— 它由用户直接设定,系统只承担实现义务。
