# Agent Team 协作责任模型

日期：2026-10-21
状态：当前实现语义

本文定义 Agent Team 的契约、调度、工作项、审查、接受和收尾责任。实现接口见[技术设计](./collaboration-technical-design.md)，产品总览见[产品概念](./concept.md)。

## 1. 责任划分

| 角色 | 责任 |
| --- | --- |
| 用户 | 提供目标；确认建群契约与契约变更；决定继续、变更或终止 |
| 主 Agent | 整理契约；创建与调整工作项；派发；汇总证据；组织审查；接受成果；覆盖完成条件；请求收尾 |
| 执行者 | 在授权范围内完成工作，用群消息汇报成果、证据、限制和阻塞 |
| 审查者 | 独立检查指定成果版本，向主 Agent提交意见，不代写成果 |

主 Agent 拥有协作管理权，但没有契约修改权。普通成员没有工作项、接受、完成声明或收尾管理权限。角色是当前工作责任，不是全局权限等级。

团队正常收敛不依赖固定轮次。主 Agent 根据目标缺口决定继续、等待、补充、返工、接受或收尾。

## 2. 目标契约

用户先表达意图，主 Agent 将其整理为可判断完成的契约，再请求确认。契约至少包含：

- 目标与范围；
- 文件、命令、外部访问与部署等边界；
- 必须由用户确认的事项；
- 交付物和证据要求；
- 可逐项检查的完成条件；
- 执行策略。

确认绑定准备记录、具体 revision 和内容摘要。确认后契约锁定；后续修改形成新版本并再次取得用户确认。

主 Agent 可以在契约内拆解工作、调整参与者和安排审查，不能借工作项或消息解释扩大授权。等待用户决定时，只暂停依赖该决定的工作；不受影响且仍在契约内的工作可以继续。

## 3. 统一调度

同一群内，所有成员发给主 Agent 的正式消息进入唯一 coordination 会话并串行处理。不同成员可以并行工作，其汇报允许在同一回合按序合并，但必须保留每条消息的作者和工作项关联。

用户私聊独立。用户明确共享的指令通过可信控制路径写入调度上下文，但不复制整段私聊历史。普通成员之间仍可使用双人上下文。

主 Agent 不应通过宿主原生子 Agent 或阻塞式等待工具建立第二套调度。需要等待时结束当前回合，由框架在新消息到达后启动同一调度会话的新回合。

## 4. 工作项

工作项代表一项可被整体接受的成果，初版采用粗颗粒设计，允许多个成员参与。每项至少保存：

- 标题、目的和完成标准；
- 参与成员与 `executor`、`collaborator`、`reviewer` 职责；
- 从契约继承或收窄的执行策略；
- 是否要求独立审查；
- 明确成果版本、贡献证据和审查意见；
- revision 与当前状态。

允许状态：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已创建，尚未开始组织工作 |
| `in_progress` | 正在执行、协作、审查、补充或返工 |
| `blocked` | 推进依赖用户决定或外部条件 |
| `pending_decision` | 成果与必要审查齐备，等待接受判断 |
| `accepted` | 主 Agent 确认成果可用于完成目标 |
| `cancelled` | 不再继续，已记录合法责任去向 |

状态转换由框架集中校验。已接受成果发生变化时必须先重开；取消不等于完成，也不能抹去仍未覆盖的契约责任。

工作项的 `policy` 表示这项工作实际需要的最高项目访问范围，`allowShell` 表示是否需要命令。角色运行时再做收窄：

- 主 Agent普通 coordination 回合固定为 `communication`；
- executor/collaborator 使用工作项策略；
- reviewer 最多为 `read-only`；
- 纯消息任务使用 `communication`。

契约仍是不可突破的授权上限。框架计算逻辑策略域，Adapter 决定复用还是轮换物理会话；策略变化不能产生未确认的权限扩大。

## 5. 证据、审查与接受

成员用自然语言消息汇报。主 Agent 将实际消息编号登记为贡献或审查引用，不要求另建提交或审查模板。

贡献证据必须来自该项的执行者或协作者。审查意见必须来自独立审查者，并引用同一成果版本。成果更新后，旧审查不能自动覆盖新版本。

进入 `pending_decision` 或 `accepted` 前，成果、贡献证据及契约要求的审查必须已经齐备。审查是否充分和成果质量由主 Agent 判断；框架只校验作者、归属、版本和状态等结构事实。

接受决定保留理由和分歧处理。主 Agent 不同意审查意见时必须说明依据，不能改写原意见或让质量问题消失。

## 6. 收尾

目标完成需要：

1. 每项工作项已接受，或已合法取消并说明责任覆盖；
2. 每项契约完成条件都有已接受成果覆盖；
3. 必要审查已完成，重要分歧已处理；
4. 所有未处理正式消息都有处理去向；
5. 持久最终交付已提交。

`team_finish` 先原子检测上述结构条件，再设置 `closing`。仍有未处理消息时拒绝收尾并返回消息编号，避免进入无法继续派发的卡死状态。

收尾工具的返回只表示收尾意图已保存。调用工具的回合必须实际结束，且不能存在未处理消息或待核实运行，团队才变为 `closed`。

`closing` 阻止新增普通派发。用户可以撤回尚未结束的收尾，恢复工作并保留原因。

## 7. 无法完成

必要材料、用户决定或外部条件缺失时，主 Agent 如实保留 `blocked` 工作项，说明已完成内容、缺失证据和待决定问题，不能自行降低完成条件。

只有用户可明确终止未完成任务。终止后保存 `outcome: incomplete`、原因和未完成工作，并停止团队运行。目标未完成但运行已经停止时，不能显示为完成。

## 8. 可信入口

用户确认、契约变更决定、终止、撤回收尾和核实不确定运行来自 CLI/后续桌面可信入口。Agent 工具不能批准契约或伪造用户决定。

面板只读展示契约、工作项、证据、接受、待决定、最终结果和运行状态，不提供聊天、确认或管理写入口。
