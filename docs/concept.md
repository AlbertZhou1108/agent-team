# Agent 团队协作框架 · 概念设计

- 日期：2026-10-21
- 状态：概念稿 v0.5（v0.4 已由用户确认；纳入后续澄清，进入技术验证）
- 范围：业务需求、业务流程、核心概念、架构方向、边界与风险。不含具体实现细节与排期。
- 变更：v0.2 宿主改为开放集合；v0.3 能力改为成员自述；v0.4 明确能力自述更新与介入边界；v0.5 纳入用户确认的双人独立会话、轻通知留言、恢复发送与访问撤销。

> 术语约定：本文中“团队”与“群”同义，领域模型里统一叫 **群 Group**；“主 Agent”是用户当前聊天的 Agent 身份；“成员”是群里的 Agent 身份，包含主 Agent 与普通成员；成员与宿主会话分离。宿主不限于文中举例的 Codex / DSH / Claude Code，它们只是首批参考实现。

## 已确认的补充决策（v0.5）

**当前实现顺序（用户确认）**：先实现 CLI 版本，之后再适配桌面应用。CLI 与桌面端仍分别验证；同时支持并可自由选择是最终目标，至少一种入口可用是接入底线。


**接入入口补充（用户确认）**：每种宿主最好同时支持 CLI 与桌面应用，由用户自由选择。最低要求是该宿主至少一种入口可接入，不要求两者全部通过才能使用。CLI 与桌面端分别验证、分别说明实际可用范围；一种入口通过不能代表另一种也通过。主 Agent 与普通成员的适用范围也分别记录。


以下决定来自用户评审后的澄清，用于明确后文的概念边界。

1. **成员与会话分离**：成员是群里的身份；双方的独立对话由双人会话承载。同一成员可参与多段双人会话，各自保持上下文，不按成员统一串行。微观是一对一，宏观由群提供多方对话能力。
2. **主 Agent 的入口分离**：成员回复主 Agent，进入双方的独立会话，不进入用户私聊。主 Agent 向用户汇总；如何读取、汇总这些对话是本阶段重点验证项，不能假定不同宿主会话自动共享记忆。
3. **留言有两种用途**：第三个成员介入涉及自己的对话；发送比正式消息更轻的通知。仍不介入与自己无关的对话。
4. **留言作为下一条正式消息的一部分**：按接收成员积累；不要求下一条正式消息来自留言发送者。把留言与正式消息合成一次宿主输入，不单独触发回合；没有正式消息则继续等待。
5. **恢复发送由框架负责**：持久保留恢复发送必需的最少技术进度；重启后继续发送未发出的消息，不要求主 Agent 手工重发。技术进度不是任务、完成或审查状态，也不向产品引入已读、已投递状态。
6. **重复仅用消息编号识别**：首次生成唯一消息编号，重发沿用；不增加重发标记。相同编号表示同一条消息。编号可辅助识别，不等于保证副作用绝不重复。
7. **移除立即撤销框架访问**：停止会话即使失败，也不得继续通过框架读记录、发消息或更新群内自述。历史身份与消息保留；已进入宿主上下文的内容无法收回。

## 0. 一句话

一个本机、单用户的 Agent 团队协作框架：把本机可驱动的 Agent 会话（如 Codex、DeepSeek Harness、Claude Code）组合成团队；主 Agent 是用户唯一入口；成员能力由成员自述、全群可见；框架只负责“群、消息记录、唤醒路由”，不保存任务状态。

## 1. 背景与目标

### 1.1 旧项目的问题

旧项目（collab-scene）在“任务/团队”这层堆了太多业务状态：工作项、完成条件、审查记录、团队生命周期、绑定/凭据/授权审计、投递状态机、多版本兼容、发布与运维。这些状态互相引用、互相校验，最终导致用户实际感受到的五个问题：

1. 派工/投递不可靠；
2. 审查链路不可信；
3. 状态不可信；
4. 环境与启动太重；
5. 流程太绕。

结论：新项目不是把这套状态机修好，而是把“业务状态”这一整层删掉。

### 1.2 新项目的目标

- 单用户、本机、每天真用；
- **宿主开放**：种类与数量不固定（Codex / DSH / Claude Code 只是首批参考）；任何能被框架驱动会话的 Agent 宿主都能接入，并尽量既能当主 Agent 也能当成员；
- **能力由成员自述**：每个成员在入群时说明自己能做什么，其他成员可以读到并自行判断找谁；自述只有本人能更新；框架不做能力分级、不做强制路由；
- 像一个 Agent 的团队/群：有成员、有工作目录、有消息记录、有面板；但消息投递是 1:1；
- 简单、可信：没有任务状态、没有团队生命周期、没有业务投递状态机；允许最少恢复发送技术进度；执行事实以宿主会话为准。

### 1.3 第一原则

> **会话是 1:1 的；团队只是多个 1:1 的组合。**

所有设计决策从这一条推导。

## 4. 关键设计决策

### D1 会话 1:1，团队是组合

群内每对成员之间是独立的 1:1 对话。宿主会话承载各方上下文，具体映射由适配器验证；不能把一个成员固定等同于一个宿主会话。群通过共享记录与留言组合这些双人对话。

- 每条消息只有一个接收者；
- 要跟两个人都说，就分别发两条；
- 成员之间两两可以直接对话，不需要主 Agent 中转。

### D2 只唤醒接收者

框架只把“发给某个会话的消息”作为新回合交给它；不把别人的消息推给它，不做旁听，不做广播唤醒。

- 没有“全员被叫醒”；
- 没被点名的成员不会因为这条消息而动；
- 唤醒失败时如实告诉发送者，不假装成功；崩溃重启后恢复未发出的消息，沿用原消息编号。

### D3 消息记录共享，读不读由成员决定

框架保存完整的群消息记录。成员在自己的回合里，可以自己决定要不要读、读多少；框架不主动推送别人的消息。

- 记录共享是“可读”：成员需要上下文时可以查；
- 不是“推送”：没发给它的消息不会进入它的会话；
- 读到不属于自己的消息后，它只在对话涉及自己部分时，才用留言轻量联系相关人（见 D4、D14 与 R11）。

### D4 消息分两种：对话消息与留言

| 类型 | 语义 | 是否唤醒接收者 |
| --- | --- | --- |
| **对话消息** | 回复、点名、需要对方接着做的事 | 唤醒 |
| **留言** | 介入涉及自己的对话，或发送较轻的通知；对方不必立刻处理 | **不唤醒**，随发给接收成员的下一条正式消息组成一次输入，发送者可不同 |

- 默认：回复用对话消息；不介入与自己无关的对话；涉及自己的部分用留言；
- L1 是初始策略，需实测；
- 回退方案：若留言仍然造成干扰，则关闭留言能力——成员只能回应发给自己的消息；读取是否也收回，到时再定。

### D5 无任务、无状态、无生命周期

框架没有任务实体、没有任务状态机、没有完成条件、没有审查记录、没有团队生命周期。

- 消息就是自然语言；
- 是否完成、是否继续、是否重做，由主 Agent 和用户判断；
- 框架不保存“进行中/已完成/失败”这类业务状态；
- 执行事实以宿主会话为准。

### D6 主 Agent 的两个说话面分离

主 Agent 同时是“用户的对话对象”和“群成员”，两个说话面必须分开：

- 在宿主聊天里的输出 → 给用户看；
- 在群里的发言 → 通过工具发送，给成员看；
- 用户与主 Agent 的私聊不进群消息记录；
- 主 Agent 拿不准时先问用户，再决定是否转达到群里。

### D7 单进程中心群总线

采用一个本地单进程作为“群总线”：

- 保存群配置与消息记录；
- 负责消息路由、唤醒队列、失败上报；
- 对 Agent 暴露工具（MCP / 宿主插件等形式）；
- 内置只读面板；
- 通过一组宿主适配器（首批参考 Codex / DSH / Claude Code）操作会话；适配器只需要能驱动会话，不需要给宿主或成员分级。

它不是工作流引擎：不保存业务状态，只做“记录 + 路由 + 唤醒 + 观测”。

### D8 框架的职责边界

框架负责：群配置、消息记录、唤醒、面板、会话启动/停止（尽力而为）、失败上报。

框架不负责：任务拆解、质量判断、完成判定、审查结论、成员角色分工、工作区写锁、模型额度管理、成员能力分级、宿主能力差异的兼容矩阵。

### D9 面板只观测

面板展示群、成员、消息流、成员会话历史；**不提供聊天输入**。用户与 Agent 的所有交互都通过主 Agent。

### D10 共享工作目录，框架不管写锁

每个群有一个共享工作目录；承载群对话的宿主会话启动时以它为工作目录。

- 框架不提供文件锁/租约；
- 并发写冲突由主 Agent 协调；
- 这是已知限制，不在这版引入锁机制。

### D11 群删除 = 删配置与记录 + 尽力停止成员会话

- 删群时停止框架启动的成员会话（尽力而为）；
- 删除群配置与消息记录；
- 宿主里的会话历史不删（那是宿主的事实）；
- 用户与主 Agent 的私聊会话不受影响；群内双人会话按框架启动的会话清理。

### D12 失败如实上报，重启恢复未发送消息

- 成员启动失败：告诉主 Agent（谁、什么错），由用户决定重试/换人；
- 唤醒失败：以系统通知告诉发送者；
- 框架不提供“已投递/已读”业务状态；普通失败如实上报，重启后恢复未发出的消息。

### D13 能力由成员自述，不由框架分级

框架不维护“能力标签/能力等级/谁能做什么”的分类。每个成员在入群时用一段自然语言说明自己能做什么；其他成员通过成员列表读到它，自行判断要不要找它。

- 自述是**参考信息**，不是授权，也不是路由规则；
- 只有成员本人能更新自己的自述；其他成员、主 Agent、框架都不能代改；
- 框架不校验自述真假，也不根据自述拦截/强制任何消息；
- 主 Agent 可以基于自述来决定分工，但决定权在发起者。

### D14 介入边界：不介入无关对话，涉及自己的部分用留言

- 成员可以读记录，但不主动介入与自己无关的对话；
- 如果他人对话涉及自己的部分（例如在讨论自己的产出），可以用留言轻量联系相关人（不唤醒）；
- “是否涉及自己”由成员自己判断，框架不做语义判断、不强制拦截；
- 规则写进入群说明；实测效果不好时关闭留言，只允许回复。

## 5. 核心概念

### 5.1 概念表

| 概念 | 定义 | 不是什么 |
| --- | --- | --- |
| **群 Group** | 一个团队空间：名称、工作目录、主 Agent、成员集合 | 没有生命周期状态；不是任务容器 |
| **成员 Member** | 某个 Agent 在某个群里的身份：显示名 + 角色（主/普通）+ 能力自述；可参与多个双人会话 | 没有职责字段、没有权限等级、没有任务归属 |
| **能力自述 Profile** | 成员用自然语言说明自己能做什么；入群时自述、仅本人可更新；所有成员可读 | 不是能力等级；不是授权；不用于强制路由 |
| **宿主 Host** | 提供 Agent 会话的运行时（如 Codex / DSH / Claude Code，也可是其他 Agent） | 不是固定清单；不是框架的一部分 |
| **会话 Session** | 双人对话的宿主载体；群内双方对应独立对话上下文；宿主类型 + 会话引用；运行事实从宿主读 | 不是框架维护的状态 |
| **消息 Message** | 一条 1:1 发言：发送者、接收者、类型（对话/留言/系统）、正文、时间、可选回复锚点 | 没有已读/已投递/处理中状态 |
| **消息记录** | 所有消息的追加式记录；成员可按需读，面板全量可见 | 不是任务账本；不做状态推导 |
| **唤醒 Wake** | 把消息变成接收者会话的一个新回合 | 不是业务状态；允许为重启恢复保存最少内部发送进度 |
| **主 Agent Lead** | 用户当前聊天的 Agent 身份；私聊是用户唯一入口；群内另有独立双人会话 | 不是固定宿主；不是“管理员权限”的抽象 |
| **面板 Panel** | 群、成员、消息、成员会话历史的完整观测视图 | 不是聊天入口 |
| **工作目录 Workspace** | 群共享的文件目录；成员会话的工作目录 | 不是权限边界（框架不强制文件访问） |

### 5.2 概念级数据

框架只保存以下数据（具体存储实现另定）：

**群**
- id、名称、工作目录、主 Agent 成员 id、用户私聊入口引用、创建时间

**成员**
- 成员 id、群 id、显示名、宿主类型（开放字符串）、角色（主/普通）、入群时间、能力自述（自由文本，仅本人可更新）

**双人对话**
- 群 id、双方成员 id、各方需要的宿主会话引用（具体映射待宿主验证）；用户私聊入口单独保留

**内部技术进度**
- 恢复发送所需的最少持久信息、留言随正式消息交付的进度；不表示任务完成，不做业务状态推导

**消息**
- id、群 id、发送者、接收者、类型（对话/留言/系统）、正文、回复锚点（可选）、时间

**没有**：任务、完成条件、审查记录、业务投递状态与生命周期。仅保留身份到会话的技术映射、访问校验及恢复发送所需信息，不恢复旧项目的绑定/凭据业务实体。

### 5.3 唤醒

**定义**：让一个空闲会话开始一个新回合，把“发给它的消息”和必要上下文交给它。

**输入**：

- 发给它的消息（若积压，则一次列出全部待处理消息）；
- 群标识、成员列表与能力自述（或可查询）；
- 工具说明（send / note / read / members / profile.set）。

**触发**：

- 收到“对话消息”的接收者；
- 不触发：留言的接收者（留言随发给它的下一条正式消息进入同一次宿主输入）。

**队列**：

- 每个双人会话同时只跑一个回合；不同双人会话不按成员统一排队；
- 同一双人会话的回合进行中到达的正式消息等待，不打断当前回合；
- 积压消息合并成一次唤醒，按顺序列出；
- 唤醒失败以系统通知告诉发送者。

### 5.4 不变量

1. 消息只追加，不修改、不删除。
2. 每条消息有且只有一个接收者。
3. 只有接收者会被唤醒；没有旁听、没有广播。
4. 唤醒只带发给它的消息；成员要更多上下文就自己读记录。
5. 每个双人会话同时只跑一个回合；不同双人会话不按成员统一排队；期间消息排队、合并。
6. 回复用对话消息（唤醒）；不介入无关对话；涉及自己的部分或发送轻通知用留言（不唤醒）。
7. 用户不是群成员；用户与主 Agent 的私聊不进群记录。
8. 执行事实以宿主会话为准；框架不保存业务状态。
9. 群没有开始/结束/暂停状态；建了就在，删了才没。
10. 发送者明确指定接收者，框架不猜收件人。
11. 能力自述只作参考，不用于强制路由、授权或能力分级。
12. 能力自述所有成员可读，只有本人可更新。
13. 不介入与自己无关的对话；涉及自己的部分或发送轻通知可用留言；框架不做语义判断。

## 6. 业务流程

### 6.1 开群

1. 用户在任意宿主里对主 Agent 说：“开个团队，讨论一下这套 UI 设计。”
2. 主 Agent 提议成员（宿主 + 模型），用户确认；成员数量和宿主种类不固定。
3. 主 Agent 调建群工具：群名、工作目录、成员列表。
4. 框架逐个启动成员会话，并给每个成员发一条入群说明：
   - 它是谁、群里有谁、工作目录；
   - 能用的工具；
   - 规则：1:1 消息、记录可自行读取、**不介入与自己无关的对话、涉及自己的部分或发送轻通知可用留言**、没有任务状态；
   - 请成员用一段话说明自己能做什么（调用 `profile.set`）。
5. 成员的能力自述进入成员资料，所有成员和面板可见；只有本人能更新。
6. 任何成员启动失败：如实告诉主 Agent（谁、什么错），由用户决定重试/换人；不静默降级。
7. 主 Agent 在宿主聊天里向用户确认“群已就绪”，并可把成员能力自述一并告知用户。

### 6.2 1:1 派活

1. 主 Agent 读成员能力自述，决定分工（例如 DSH 自述擅长配色，Claude 自述擅长质感）；任何成员也可以根据自述直接找另一个成员。
2. 主 Agent 发对话消息给 DSH：“看看配色。”
3. 主 Agent 发对话消息给 Claude：“看看质感。”
4. 框架写入消息记录（两条独立消息）。
5. 框架唤醒 DSH 和 Claude；各自收到“你有一条来自 Codex 的消息：……”。
6. 其他成员不会被唤醒。

### 6.3 成员醒来与自取上下文

1. 唤醒只交付发给它的消息（积压时是全部待处理消息）。
2. 成员判断信息够不够；不够就调读记录工具，自己决定读多少。
3. 成员发言：
   - 回复发送者 → 对话消息，唤醒对方；
   - 他人对话涉及自己的部分、需要提醒/纠错 → 留言，不唤醒对方；
   - 一回合可以发多条；也可以不发（沉默）。
4. 成员这一回合在宿主里的“最终文本”不作为群消息——群里说了什么，只由发送工具决定。

### 6.4 成员之间对话

1. DSH 发对话消息给 Claude → 消息入记录，Claude 被唤醒。
2. Claude 回复 DSH → DSH 被唤醒。
3. 主 Agent 的相关双人会话没有收到正式消息就不会被唤醒；它想了解情况，自己读记录，或由成员发给它。
4. 成员之间可以直接对话，不需要主 Agent 中转。

### 6.5 介入边界与留言

**L1（初始策略）**：成员可以读到不属于自己的消息，但**不介入与自己无关的对话**；如果他人对话涉及自己的部分（例如在讨论自己的产出），可以用**留言**轻量联系相关人（不唤醒），随发给对方的下一条正式消息一起交付，发送者可不同。

**回退（实测效果不好时）**：关闭留言能力——成员只能回应发给自己的消息；读取是否也收回，到时再定。

### 6.6 主 Agent 私下问用户

1. 主 Agent 在宿主聊天里问用户（例如“这里的质感你更想要哪种？”）。
2. 用户的回答不会自动进群；主 Agent 判断后，需要时自己发消息转达。
3. 用户不是群成员，不参与群消息。

### 6.7 汇报（没有“结束团队”）

1. 主 Agent 判断讨论够了，在宿主聊天里向用户汇报。
2. 没有“结束团队”这个动作：群还在、成员还在、消息还在。
3. 用户可以继续聊、加人、移人、删群。
4. 框架不判断任务是否完成。

### 6.8 面板观测

- 看群列表、成员列表、消息流（发送者 → 接收者）、每个成员的宿主会话历史。
- 用户不在面板里发消息。
- 面板展示的是记录与宿主会话事实，不是框架推导的状态。

### 6.9 成员变更与删群

- **加人**：启动新会话、发入群说明；历史记录对新成员可读。
- **移人**：从群移除，立即撤销该成员通过框架读写群数据的访问，并尽力停止相关会话；停止失败不影响访问撤销；历史消息与发送者身份保留。
- **删群**：停止成员会话（尽力而为），删除群配置与消息记录；宿主会话历史不删；用户私聊会话不动。

### 6.10 异常

- 成员启动失败 → 主 Agent 收到错误，用户决定重试/换人；
- 唤醒失败 → 系统通知发给发送者；
- 框架重启 → 群配置与消息记录不丢；框架恢复未发出的消息，重发沿用原消息编号；不依赖主 Agent 人工查记录重发；
- 宿主进程/会话不可达 → 以宿主事实为准，框架不臆造状态。

## 7. 架构方向（概念级）

> 本节只定方向，不锁定具体实现。

### 7.1 单进程群总线

```text
用户
 │ 宿主聊天
 ▼
主 Agent 会话（宿主 A / 宿主 B / …）
 │  send / note / read / 管理工具
 ▼
┌───────────────────────────────┐
│ 群总线（单个本地进程）          │
│  · 群配置 + 消息记录            │
│  · 消息路由 + 唤醒队列          │
│  · Agent 工具服务               │
│  · 只读面板                     │
└──────┬───────────────┬─────────┘
       │               │
       ▼               ▼
  成员会话 A       成员会话 B
（任意可被驱动的宿主）
```

### 7.2 组件职责

| 组件 | 职责 |
| --- | --- |
| 群总线进程 | 保存群配置与消息记录；路由消息；维护每会话的唤醒队列；提供工具与面板；失败上报 |
| Agent 工具面 | `send` / `note` / `read` / `members` / `profile.set`；主 Agent 另有建群/加人/移人/删群/列群 |
| 宿主适配器（每个宿主一个） | 让框架能驱动该宿主的会话：创建/恢复、注入回合、读历史、感知回合结束、尽力停止、暴露工具、识别会话；这是技术接入前提，不是能力分级 |
| 面板 | 只读观测：群、成员、消息、会话历史 |

### 7.3 Agent 工具面（概念级）

| 工具 | 谁用 | 作用 |
| --- | --- | --- |
| `send(to, text)` | 所有成员 | 发一条对话消息；唤醒接收者 |
| `note(to, text)` | 所有成员 | 介入涉及自己的对话或发送轻通知；不唤醒接收者；随其下一条正式消息交付 |
| `read(...)` | 所有成员 | 读消息记录（可按时间/发送者/条数过滤） |
| `members()` | 所有成员 | 看群成员、显示名与能力自述 |
| `profile.set(text)` | 所有成员 | 更新自己的能力自述（只能改自己的） |
| 建群 / 加人 / 移人 / 删群 / 列群 | 主 Agent | 管理群 |

### 7.4 宿主接入要求与成员能力（待验证）

这里有两层，不要混在一起。

**第一层：宿主接入要求（技术前提，实现层）**

框架要驱动一个宿主会话，适配器必须能做到：

1. 会话创建 / 恢复；
2. 注入回合（唤醒）；
3. 读取会话历史；
4. 感知回合结束与产出；
5. 停止 / 打断（尽力而为）；
6. 向会话暴露框架工具（send / note / read / members / profile.set）；
7. 识别会话身份（主 Agent 登记、工具调用来源）。

这些是“框架能不能用这个宿主”的技术前提，不是给宿主或成员打分。做不到的宿主不能接入；部分做不到的，按实际可用范围使用，不贴“受限等级”标签。

**第二层：成员能力自述（产品层）**

成员能力不由宿主类型推断，也不由框架分类：

- 成员在入群时用自然语言说明自己能做什么（`profile.set`）；
- 所有成员都能通过 `members()` 读到彼此的能力自述；
- 只有成员本人能更新自己的自述；其他成员、主 Agent、框架不能代改；框架不校验真假；
- 自述只作参考：主 Agent 或任何成员可以据此决定找谁，但框架不强制路由、不做授权、不做能力分级。

**首批参考适配器**：

| 宿主 | 会话形态 | 需要验证的技术前提 |
| --- | --- | --- |
| Codex | app-server 线程 / 队列 | 创建/恢复会话、注入回合、读历史、回合结束、打断、会话识别 |
| DSH | 宿主内 session（插件） | 创建会话、注入回合、读历史、回合状态、停止、工具暴露 |
| Claude Code | 逻辑会话（headless / SDK） | headless 恢复与会话注入、主 Agent 交互式会话能否被外部唤醒、读历史、打断、工具暴露 |
| 其他 Agent 宿主 | 视其会话模型 | 按同一技术前提接入；缺哪项就显式说明哪项做不到 |

> 首批参考宿主只是验证接入的样本，不是白名单。框架代码里不写死宿主列表。

### 7.5 启动与轻量

- 一条命令启动群总线；面板地址在启动结果里给出；
- 不做安装器、launchd 托管、发布快照、版本兼容矩阵；
- 数据落在本机一个文件里；不引入外部数据库服务。

## 8. 方案取舍记录

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| A. 单进程中心群总线 | **采纳** | 路由、队列、面板、恢复集中在一处；代码最少；行为可推理 |
| B. 无中心，“工具即框架” | 否决 | 并发、顺序、去重、恢复、面板聚合会变成分布式协调；复杂度只是搬家 |
| C. 复用 Matrix/IRC 等聊天基础设施 | 否决 | 引入额外服务与运维、安全边界；与“轻”冲突 |
| D. 真 QQ 群：全员推送/旁听 | 否决 | 底层会话是 1:1；全员唤醒成本高、易抢话/跑题；与“只唤醒接收者”冲突 |
| E. 完整任务看板 | 否决 | 旧项目过度设计的主要来源；任务状态与宿主事实容易不一致 |

## 9. 明确不做（非目标）

- 任务/工作项实体、任务状态机、完成条件、审查记录、返工预算；
- 团队开始/结束/暂停/关闭；
- 旧项目的绑定/凭据业务实体、授权审计、业务投递状态机、已读/已投递状态；最少会话映射、访问校验及恢复进度除外；
- 能力标签体系、能力等级、按能力强制路由；
- 语义级的“是否与自己相关”判断与强制拦截；
- 多用户、远程、账号、租户、云服务；
- 模型额度管理、计费、调用配额；
- 旧项目数据迁移、旧协议兼容、第三方宿主插件市场、版本兼容矩阵；
- 由框架判断任务完成、代码质量、审查结论；
- 工作区文件锁/租约（本版不做，主 Agent 协调）；
- 面板聊天输入。

## 10. 风险与待验证

| # | 风险 | 影响 | 验证/应对 |
| --- | --- | --- | --- |
| 1 | 部分宿主（如 Claude Code 交互式会话）能否被外部注入回合 | 该宿主无法当主 Agent | 优先实测；不成立则用 headless/SDK 会话替代，或明确告知该宿主不能当主 Agent |
| 2 | 主 Agent 会话识别（工具调用来自哪个会话） | 无法正确唤醒主 Agent / 多群路由错乱 | 每个宿主验证会话标识暴露；必要时用宿主启动的会话 |
| 3 | 宿主工具暴露方式不同（MCP / 插件 / …） | 无法统一工具面 | 验证每类宿主的工具接入方式，纳入技术接入前提 |
| 4 | 面板读取成员宿主会话历史 | 面板不完整 | 验证各宿主历史读取能力；不成立则降级展示 |
| 5 | 介入边界与留言策略的实际效果（“与自己相关”靠成员判断） | 误介入、漏介入，或留言没人看 | 规则写进入群说明；实测；不行就关闭留言，只允许回复 |
| 6 | 主 Agent 被群消息唤醒时，宿主聊天窗口的可见输出 | 用户聊天被内部事件打扰 | 实测；必要时约定主 Agent 在群事件回合少输出 |
| 7 | 框架重启丢失未发出的唤醒 | 消息在记录里但没人被叫醒 | 框架持久保留最少发送进度并恢复发送；重发沿用原消息编号 |
| 8 | 共享工作目录并发写冲突 | 成员互相覆盖 | 主 Agent 协调；实测后决定是否引入隔离 |
| 9 | 长会话上下文/成本 | 上下文膨胀、token 成本上升 | 成员按需读记录；唤醒只带新消息；后续观测 |
| 10 | 多群共用主 Agent 会话 | 唤醒消息缺少群上下文/路由歧义 | 唤醒输入带群与双人对话标识；用户私聊入口独立；实测 |
| 11 | 用户私聊与群消息边界 | 误把私聊转进群 | 靠主 Agent 判断 + 工具分离 |
| 12 | 新增宿主的技术接入成本 | 接入慢、行为不一致 | 先定技术接入前提与验证清单；不做兼容矩阵 |
| 13 | 成员能力自述可能夸大、过时或不可靠 | 分工误判 | 自述仅本人可更新、面板可见、仅作参考；不用于强制路由 |

## 11. 成功标准

### 11.1 标准场景（更新版）

用户在 Codex 里说“开个团队讨论这套 UI 设计”：

1. Codex 创建群，拉 DSH 和 Claude 进来（这里只是示例；换成其他宿主同样成立）；成员入群时自述能力，Codex 据此分工；
2. Codex 分别 1:1 对 DSH 说“看看配色”，对 Claude 说“看看质感”；
3. 两人回复；Codex 和 Claude 反复交流；Codex 有拿不准的，私下问用户，用户回答后继续；
4. 如果 Codex 与 DSH 的交流涉及 Claude 自己的部分、且 Claude 发现说法有误，Claude 可以给 Codex 发**留言**（不唤醒）；Codex 下次醒来时看到；
5. Codex 认为设计讨论够了，向用户汇报；
6. 全程用户在面板能看到群、成员、消息和成员会话，不需要手动搬消息；
7. 没有任务、没有状态、没有“开始/结束团队”。

### 11.2 验收观察点

- 首批参考宿主（Codex / DSH / Claude Code）都能当主 Agent 或成员；新增宿主按技术接入前提接入；
- 成员能读到彼此的能力自述，并据此决定找谁；
- 消息 1:1 送达；只有接收者被唤醒；
- 成员能在回合内自主读记录；
- 留言不唤醒接收者；
- 成员不介入与自己无关的对话；涉及自己的对话可用留言，也可用留言发送轻通知；
- 能力自述所有成员可读，只有本人能更新；
- 面板展示的是真实记录与宿主会话；
- 框架重启后群与消息记录不丢；
- 全程无人工复制粘贴；
- 数据与界面里没有任务/状态/生命周期概念。

### 11.3 失败判据

- 需要用户手动在 Agent 之间搬消息；
- 状态与宿主会话事实对不上；
- 一个成员的异常导致整个团队卡死；
- 启动/安装仍然需要多步手工运维；
- 实现里重新出现任务状态机、生命周期或业务投递状态；恢复发送的最少技术进度不属于此项；
- 宿主列表在代码里被写死，新增宿主需要改核心逻辑；
- 框架给成员贴固定能力标签，或按能力等级强制路由；
- 成员可以随意介入无关对话，或框架试图做语义级的“相关性”判定。

## 12. 开放问题

1. 部分宿主（如 Claude Code 交互式会话）无法被外部唤醒时，如何明确告知“不能当主 Agent”，而不是靠能力分级。
2. 主 Agent 私聊入口与多段双人会话如何被识别、关联，以及如何汇总对话。
3. 已决定不引入留言已读/未读状态；仅维护随正式消息交付的内部进度。
4. 已决定框架承担重启恢复发送；最少持久信息与恢复边界由技术验证确定。
5. 删群时是否一定要停止成员会话，还是只解除绑定。
6. 同一主 Agent 会话同时带多个群时，唤醒上下文如何路由。
7. 面板按双人会话与群时间线的展示方式。
8. 是否需要“群公告/固定上下文”（当前由入群说明承担）。
9. 留言能力是否要按成员/按群单独开关（当前为全局 L1）。
