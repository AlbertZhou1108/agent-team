# Agent Team 产品概念

日期：2026-10-21
状态：当前实现产品模型

Agent Team 是本机、单用户的 CLI Agent 协作层。用户只与主 Agent 对话；主 Agent 把用户意图整理为经确认的目标契约，创建团队，组织多个宿主会话完成工作，并以实际成果、独立审查和运行事实决定接受与收尾。

## 1. 产品边界

- 单用户、本机运行；运行数据保存在本地 SQLite，不依赖外部数据库或账号服务。
- 用户是唯一真人入口，不是群成员。用户私聊不自动进入团队共享上下文。
- 主 Agent 是用户当前对话中的 Agent，也是群内唯一承担协作管理职责的成员。
- 普通成员通过真实宿主会话执行安排的工作，以自然语言群消息汇报。
- 面板用于核对契约、消息、工作记录、宿主事件、模型观测和真实运行状态；侧栏设置可切换本地主题并保存全局模型策略。
- 框架负责身份、契约、状态流转、消息路由、运行记录和结构性校验；文件内容质量与业务取舍仍由主 Agent 和审查者判断。

当前 CLI 接入 Codex app-server、Claude Code print 模式和 DSH headless。其他宿主可通过适配器接入；CLI 可用不代表桌面应用可用。

## 2. 核心对象

| 对象 | 含义 | 关键约束 |
| --- | --- | --- |
| 群 Group | 一个长期团队空间、共享工作目录和成员集合 | 可依次承载多个目标；同一时间只有一个活动目标 |
| 目标版本 Goal Version | 群内一次由用户确认的执行循环 | 新目标增加版本；历史工作项和交付不跨目标复用 |
| 契约 Contract | 当前目标的范围、边界、确认事项、交付方式、完成条件和执行策略 | 用户确认具体 revision 与摘要后锁定；同目标内变更增加契约版本 |
| 成员 Member | 主 Agent 或普通成员在群内的永久角色身份 | 角色与会话绑定；名称在团队历史中唯一；删除后身份终止 |
| 工作项 Work Item | 一项可被整体接受的成果及参与职责 | 粗颗粒、可多人；主 Agent 管理 |
| 消息 Message | 一位发送者发给一位接收者的正式汇报、留言或系统通知 | 正文不可由管理工具改写 |
| 回合 Turn | 框架驱动一次宿主运行的尝试 | 与消息编号、宿主会话编号分别记录 |
| 目标执行阶段 | `active → closing → closed` 表示当前目标的执行状态 | `closed` 不删除或停用群；完成和失败目标都保留群通信 |

工作项状态为 `pending`、`in_progress`、`blocked`、`pending_decision`、`accepted`、`cancelled`。允许的状态转换由协作模块集中校验；返工或重开回到 `in_progress`，取消必须记录责任覆盖或与目标无关的依据。

## 3. 建群与会话

建群前，主 Agent 在当前 CLI 对话中与用户明确目标契约。准备记录只关联契约草案和确认，不代表已经创建团队，也不触发成员自述或任务执行。

用户确认绑定 preparation、revision 和内容 hash。群、首版契约与初始成员在同一事务中建立；重复确认返回同一个群。Agent 没有批准工具，不能自批、引用模糊同意或绕过准备流程直接建群。

同一群内：

- 所有成员发给主 Agent 的正式汇报进入唯一 coordination 会话，排队且串行。
- 用户私聊使用独立 private 会话，不把原文自动注入团队。
- 普通成员之间仍使用独立双人上下文；同一对话串行，不同对话可并行。
- 主 Agent 需要等待新信息时结束当前回合，不得用原生子 Agent 或阻塞式 `wait` 工具等待；框架会在新消息到达后启动同一调度会话的新回合。

成员能力通过入群自述记录，是分工参考，不是授权或能力等级。成员不能代写他人自述。

## 4. 契约与执行策略

有效契约包含：

- `goal`：用户目标；
- `scope`：允许开展的业务范围；
- `boundary`：文件、命令、外部访问及其他禁止事项；
- `confirmation`：哪些重大决定必须由用户确认；
- `delivery`：成果和证据应如何交付；
- `criteria`：主 Agent 最终必须覆盖的完成条件；
- `policy`：`communication`、`read-only` 或 `workspace-write`；
- `allowShell`：契约是否明确允许必要命令。

契约是团队授权上限，不是每个会话的默认权限。工作项声明实际访问需求及是否需要命令；主 Agent普通协调默认仅沟通，执行者/协作者按工作项需求运行，审查者自动收窄为只读。只有主 Agent被明确列为执行参与者时，相关回合才获得项目权限。

工作项及实际回合都不能超过契约上限。框架把有效策略分为 `communication` 与 `project` 两个逻辑域；Adapter 决定能否复用宿主会话。Codex 使用沟通与项目两个 thread，Claude/DSH 可复用同一 session。每个真实回合都记录请求策略、实际机制、覆盖范围和会话域。

三类保障分别存在：

1. 自然语言说明要求模型理解边界；
2. 框架校验身份、状态、版本、引用和管理权限；
3. 宿主工具裁剪与沙箱在已验证范围内阻止实际操作。

不能把第 1 层写成强制隔离，也不能把宿主文件策略推导成全面网络隔离。框架数据目录、控制凭据和任意本机绕过路径仍属于宿主与环境边界。

## 5. 工作、审查与接受

主 Agent 根据契约创建和调整工作项，明确成果、完成标准、参与成员及 `executor`、`collaborator`、`reviewer` 职责。多人可以共同负责一个成果，不要求拆成每成员一项。

成员通过自然语言 `send` 汇报，不增加强制交付模板。主 Agent 在写入成果和审查引用时必须给出实际消息编号：

- 贡献证据必须来自参与的 executor/collaborator；
- 审查意见必须来自参与的 reviewer，不能是成果作者；
- 审查必须引用与当前成果相同的明确版本；
- 成果变化后旧审查不能自动覆盖新版本。

审查意见、接受决定和工作项状态是不同事实。进入 `pending_decision` 或 `accepted` 前必须已有成果、贡献依据及契约要求的独立审查；主 Agent 负责质量判断和接受理由。

主 Agent 的管理写操作使用整体 revision、工作项 revision 和 `operationId`。过期写入被拒绝；同一操作编号和同一命令幂等返回，同一编号用于不同命令被拒绝。

## 6. 消息与恢复

- `send(to,text)`：发给一位成员并唤醒对应上下文；发给主 Agent时进入 coordination。
- `note(to,text)`：不单独唤醒，随接收者下一条正式消息合并交付。
- `read`、`members`、`profile_set`：按身份读取记录或更新本人自述。
- 工具调用来源、回合、原生调用编号和消息编号由框架附加，模型不能自报。

框架持久保存输入、附件关系和每次运行尝试。普通失败不自动重试；用户可用 `/retry` 明确重试。进程重启时，没有明确结束事实的运行标为待核实，不因内存 Map 为空就认定宿主已停止，也不自动重放可能产生副作用的旧输入。

## 7. 完成、收尾与未完成

“目标完成”和“成员已停止”是两个独立事实。

正常收尾前，主 Agent 必须：

1. 将工作项关闭为 accepted 或 cancelled；
2. 用已接受成果覆盖每个契约完成条件；
3. 引用必要审查并处理重要分歧；
4. 为所有尚未处理的正式消息给出 disposition；
5. 提交持久最终交付和收尾理由。

`team_finish` 在收尾事务中检测未处理消息。若存在遗漏，工具拒绝进入 `closing` 并返回精确消息编号；补齐后才写入收尾意图。调用工具的回合实际结束后、没有待处理消息和待核实运行时，团队才变为 `closed`，最终交付写入可信用户输出。

`closing` 阻止新的普通派发。尚未完成的收尾可由用户撤回并恢复 `active`。目标完成或失败终止并进入 `closed` 后，群、成员、会话与历史继续保留，通信入口保持开放；没有消息时不运行。后续回合默认仅沟通，可解释成果、诊断失败和追问，但不能读写项目、改写上一目标工作项、重新派工或扩大旧契约权限。

目标无法完成时，用户可明确终止；团队保留未完成工作项、阻塞证据和 `incomplete` 结果，不能用取消或降低完成条件伪装成功。

用户要求新的执行任务时，主 Agent通过 `next_goal_request` 提交完整契约，用户批准后目标版本增加、群重新进入 `active`。新目标必须建立独立工作项与证据；上一目标的成果不能覆盖新完成条件，上一目标记录保持只读。

角色与会话采用永久绑定。删除角色即永久结束该成员身份和会话关系，名称不会释放；重新执行同类职责必须创建新名称、新成员 ID 和新会话。旧消息、贡献和双人会话保留为只读审计记录，不提供恢复旧角色的操作。

## 8. 面板与隐私

面板读取公开群事实：

- 群、成员和能力自述；
- 有效契约、完成条件、工作项和 revision；
- 消息、贡献与审查引用、接受记录；
- 待用户决定、最终结果、收尾阶段、未处理消息和待核实运行；
- 群内会话的真实宿主事件、模型变化和执行轨迹。

“团队观测与指令”页提供向当前 Main Agent 发送团队指令的输入入口，但不开放通用 RPC、角色管理或契约代批。指令经幂等请求编号、Host/同源、当前 controller 和业务权限校验后进入 coordination；主 Agent 忙碌时排队，页面显示排队、投递或失败状态。全局模型策略不追溯修改已有角色，但会影响已有团队之后新增的角色。Panel Agent 提供独立的全局私人会话、团队准备确认和 Main Agent 接管入口。用户私聊原文不进入共享消息、公开 history 或群内轨迹；只有明确提交给团队的正式指令才会进入共享记录。

DSH headless 对部分事件字符串有自身截断，面板不是宿主原生历史查看器的替代品。宿主历史仍以各宿主为准。

## 9. 非目标与已知限制

- 不是工作流引擎、项目管理平台、多用户聊天或通用沙箱。
- 不提供成员广播聊天或完整即时通讯能力；团队指令只面向当前 Main Agent，也不表示目标完成。
- 不提供工作区文件锁；成员必须协调修改范围。
- 不接管已经在其他终端或桌面窗口运行的官方交互式会话；当前 CLI 由框架创建和恢复。
- Claude/DSH 尚无独立验证的持久入队回执，成功结束后才确认输入；崩溃窗口可能重发同一消息编号。
- 宿主能力会随版本变化，升级后必须重新验证策略、恢复和历史事件。
