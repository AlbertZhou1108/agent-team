# 消息附件最小设计

状态：提案。2026-10-31。按讨论收缩首期范围，只设计当前要实现的功能。

依据：[宿主能力验证](host-attachment-verification-20261031.md)、[真实纵向验证](host-attachment-vertical-verification-20261031.md)。实测结果是可行性依据，不代表下面功能已经实现。

执行入口：[附件实施计划](attachment-implementation-plan.md)。实现 Agent 以实施计划中的步骤、完成标准和检查命令为准；本文定义行为与契约。

## 用户行为

Panel Agent 私人会话支持常见文本文件(按扩展名白名单：.md .json .csv .yaml .js .ts .py .sh .sql .log 等约 60 种，以及 Makefile/Dockerfile/LICENSE 等无扩展名文件，统一 UTF-8 校验)与 PNG、JPEG 图片(签名 + 完整解码 + 像素上限)。类型由服务端按原始文件名的扩展名判定，客户端 Content-Type 仅作参考。GIF/WebP/HEIC、PDF/Office 等待宿主读取方式纵向验证后再扩，避免"传得上去、读不了"的静默失败。普通团队暂不开启附件，不改变现有 communication 权限。

1. 用户通过输入框选择或拖入文件。
2. 浏览器把文件内容上传到本机 Agent Team 服务，服务保存副本。
3. 输入框显示文件名、大小及上传中/可发送/失败；发送前可以移除。
4. 用户把文字与附件一起发送，也可以只发送附件。
5. 消息历史同时显示文字与附件；图片可预览，文件可下载，刷新页面后仍保留。
6. Agent 获得副本的原生图片输入或可读取路径。处理失败时给出反馈，不把上传成功说成 Agent 已读取。

不把原文件路径当附件；不把文件字节或 base64 存入浏览器草稿和消息正文。

## 副本生命周期

- 未发送的副本暂存24小时，启动或定期清理；上传中断的临时文件同样清理。
- 草稿移除附件时，服务可删除尚未绑定消息的副本。
- 已发送的副本随消息历史保留，不自动过期，不因回合完成或失败删除。
- 归档不删除附件，恢复后仍可使用。
- 当前没有历史永久删除入口，因此首期不设计永久删除、引用计数或历史附件清理功能。

每次上传保存独立副本，一份副本只绑定一条消息。首期不做附件复用、转发或去重；发送后内容不可覆盖。未知或已经绑定的附件ID不能用于另一条新消息。读取中的已发送附件不参与暂存清理。

附件模块对上层提供最小接口：上传、读取、删除未发送草稿、在消息事务中绑定、为实际回合准备宿主输入、清理过期未发送记录。HTTP、PanelSessions 和 adapter 不自行拼接存储路径。

## 最小存储

副本保存在框架数据目录 `attachments/` 子目录下（即 `<data>/attachments/`），使用服务生成的UUID文件名。附件副本属于框架数据，不进入私人工作区——工作区是用户和 Agent 的工作区域，附件字节不应污染它；这样更换工作区也不影响已有附件，无需迁移。宿主通过回合输入中的绝对路径读取副本，私人工作区概念与附件存储解耦。

Panel Agent 私人工作区提供跨系统默认值（macOS/Windows 为 `~/Documents/AgentTeam`，Linux 桌面环境同前，无桌面环境回退 XDG 数据目录）：创建或清空 Panel Agent 工作区时自动供给，开箱即用；显式选择的目录仍按原校验执行。

SQLite增加 `attachments` 表：

- id、panel_agent_id、original_name、media_type、size、storage_name、created_at。
- panel_message_id：未发送时为空，发送时绑定用户消息；用于查询消息附件。
- ordinal：同消息的附件显示顺序。

原始文件名只用于展示，不参与构造存储路径。浏览器只拿附件ID，不拿本机绝对路径。临时文件完整写入、验证通过并完成落盘后才返回上传成功；失败不返回可发送的附件。

清理只删除过期、未绑定记录。清理与发送共用串行/事务检查，不能发送一个已经被清理的附件。绑定与消息写入同事务完成。发送后的文件缺失时，历史仍显示附件名称及不可用提示，不悄悄隐藏附件。

## 接口与发送

沿用现有本地HTTP访问校验，新增：

- 上传单个文件，返回附件ID、名称、类型、大小；类型按扩展名分类，图片 inline 预览，文本以下载提供。
- 按附件ID预览图片或下载文件，检查所属Panel Agent。
- 移除尚未发送的附件。

现有 Panel 消息请求增加 `attachmentIds`。服务端检查归属、存在性、未绑定以及当前宿主能否接收。正文和附件都为空才拒绝；上传失败或能力不支持时，不自动丢附件只发文字。

发送结果未知时，不能让客户端重试创建重复消息。为 Panel 消息提供稳定的 clientMessageId，同一ID重试返回原消息；同一ID更改文字/附件则拒绝。消息及附件关联必须先持久化，再执行宿主调用；未知回合沿用现有恢复规则。

在现有设置页面增加“附件上传”设置，首期只提供三个全局配置项：

- 单文件最大大小：默认5MiB。
- 单条消息最大附件数：默认4个。
- 图片最大像素数：默认20MP。

服务端目前没有通用设置存储，因此新增专用 `attachment_settings` 单行表，不建设通用配置系统。前端读取同一份有效配置用于提示和选择校验，服务端在上传与消息提交时执行最终校验。配置值须为有限正数，文件数须为整数；界面明确标注单位。

降低限制不删除或隐藏已发送附件。新的上传和发送按最新配置校验；草稿不再满足限制时保留并提示，用户可移除附件或调整设置。这些默认值不是已验证的宿主上限；存在已知更低宿主上限时仍须满足宿主约束，并显示原因。

文本必须为UTF-8且拒绝二进制控制字符，PNG与JPEG必须完整解码（PNG 用 pngjs，JPEG 用 jpeg-js，均为纯 JS 成熟依赖）。上传流边接收边限额，文件名及路径不能逃逸受控目录。目录和文件拒绝符号链接，不直接执行上传内容。

不增加存储管理页面、容量仪表盘或全局配额。磁盘写入失败时明确报错，不删除历史附件腾空间。附件存储与工作区解耦，更改工作区不影响附件，无需迁移或阻断。

## 宿主接入

在现有 `host.run(context)` 增加内部附件列表，包含ID、类型、名称和服务解析出的副本路径。正文不拼入可见的绝对路径；需要文件清单时只在宿主调用输入中生成。

- Codex：PNG转为原生 `localImage`；TXT通过现有允许的文件读取方式读取。
- Claude Code：首期TXT和PNG均走已实测的Read工具，保留现有文本CLI入口；本期不为原生图片引入stream-json stdin改造。
- DSH：保留现有headless，通过read/read_image读取。

只对当前已验证的模型/入口且读取权限允许的组合启用。未知模型或能力不支持时显示原因，不自动切模型、入口或提高权限。不设计通用能力注册中心，不引入ACP迁移。

不新增附件投递状态机。上传/文件可用状态、现有消息/回合状态分开展示；能确认的文件准备或读取错误显示为附件错误，不能确认时不宣称读取成功。HTTP200或回合completed都不能解释为“Agent已理解文件”。

## 前端与验收

复用现有MessageComposer，通过附件列表和选择/移除事件扩展；Panel调用方负责上传和草稿。添加回形针、文件拖入和附件条，不新建一套输入框。历史消息通过结构化附件列表渲染，不从正文中解析路径。

任一文件上传中或失败时阻止发送，允许移除失败文件再发；提交成功后清空本次草稿，失败则保留。输入框折叠后仍显示附件数量和展开入口。暂存草稿刷新后恢复不是首期要求，已发送历史必须恢复。

按顺序实现并验收：

1. 上传限制设置、上传保存副本、预览/下载、未发送清理及必要校验。
2. 消息绑定、幂等提交和历史附件查询。
3. 三个实际适配器读取TXT/PNG、错误反馈与服务重启后重读。
4. 共用输入框和历史展示；确认附件-only、上传失败、重试不重复、归档保留均正常。

本期不实现普通团队附件、PDF/Office、远程宿主、附件转发复用、长期存储管理。出现真实需求时再设计，不预先建立相关表、接口或机制。
