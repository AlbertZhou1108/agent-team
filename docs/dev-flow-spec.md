# 开发流程 Spec（本仓库的开发工作流定义）

> 本文档是「我们如何开发」这套流程的唯一事实源，由 2026-11-21 流程设计会及后续补全裁决构成。
> 修订规则：流程裁决变更时先改这里，再同步 `AGENTS.md` 的「开发流程速查」段。
> 作用域：本仓库的前端、后端与桌面壳自身开发。不涉及 `agent-team` 框架的业务能力（成员/派单/协作）——流程的执行者是用户与 agent 主控会话，与框架业务解耦。

## 目标

给「概念 → 原型 → 切片与实现 → 验收 → CI → CD」全周期定义：双档判别、每阶段的输入/出口产物、人机拍板门禁、失败回路，以及 agent 在各阶段的约束机制。让 agent 开工有上下文包可依、遇分歧有停机规则、验收有清单可对。

## 非目标

- 不定义 `agent-team` 框架自身的协作功能（派单、成员会话）——那是被开发的业务。
- 不做代码签名、公证、自动更新（桌面端既定约束，CD 不含自动上线）。
- 不为判断型规则（如"实测优先"的尺度）建静态检查——这类只能靠指令文案与验收门禁。
- 不在缺乏实践样本前预建繁琐表单或概念/原型期自动检查器（先跑 2–3 轮再固化）。

## 术语与工具边界

| 术语 | 定义 |
| --- | --- |
| `spec.md` | 概念阶段出口产物：目标 / 非目标 / 已定决策 / 边界情况 / 验收标准 |
| `contract.md` | 原型阶段出口产物（实现契约）：关键样式与 token 值、组件清单（复用/新建）、状态与交互验收要点 |
| `tasks.md` | 实现前切片清单：将 spec/契约拆为独立切片（task），每个 task 自带验收标准 |
| 上下文包 | 实现 agent 开工的固定输入：`spec.md` 相关节选 + `contract.md`（如有）+ 当前 task 验收标准 + 关联文件清单 |
| `verify.md` | 验证记录：实现期局部自验 + 验收期门禁结果与端到端实机走查记录 |
| 完整档 / 轻量档 | 流程的两档执行形态；**默认完整档，降档权只在用户**（agent 只能建议降档） |
| 设想出入 | 实现期发现现状代码、契约或原型与设想不符的一等事件：**立即停下上报分歧点，禁止自行脑补** |

> **跨宿主工具原则**：流程规定的是**阶段职责与出口产物**，具体工具（如 `grill-me` / `figwright`）为推荐实现手段而非硬绑定；不同宿主或会话按当前可用工具完成对应职责即可。

## 双档判别与升降档规则

1. **完整档（默认）**：凡满足以下任一条件，走完整档：
   - 产生新的用户可见行为（新功能、交互变更、HTTP/MCP/RPC/CLI/桌面壳能力变化）
   - 产生新的设计、架构或视觉决策（新 token、新表面角色、新数据模型等）
   - 跨多模块或需要多角色/多切片协同对齐的复杂改动
2. **轻量档（需用户确认降档）**：仅限**不产生新的用户可见行为、不产生新的设计决策**的改动（参数调整、纯缺陷修复、文案微调、补测试、纯内部局部重构）。
   - Agent 判断符合轻量条件时，只可向用户**建议降档**并简述理由，经用户确认后执行。
3. **中途升档（兜底）**：轻量档执行过程中，一旦发现需要新增用户可见行为、改动设计决策或牵动契约边界，立即按「设想出入」停下上报，并提议升级回完整档。

## 完整档六阶段模型

```
1 概念讨论      推荐 grill-me 磨需求 → 产出 spec.md（+ 稀疏 ADR）          [门禁：用户拍板]
2 原型与契约    仅涉新 UI 决策时画原型 → 产出定稿原型 + contract.md          [门禁：用户拍板]
3 切片与实现    拆 tasks.md + 组装上下文包 → 治理在场编码 + 局部实机 → verify.md  [门禁：自验记录齐全]
4 验收          全量门禁(check/test/build) + 端到端实机 → 更新 verify.md     [门禁：用户确认 commit/push]
5 CI            推送触发 compatibility.yml（三平台 check + build + test）
6 CD            tag push 构建三平台产物；校验 SHA-256 后经用户确认创建 GitHub Release
```

### 阶段细则与出口条件

#### 阶段 1：概念讨论
- **职责**：对齐需求边界、非目标、关键取舍与可测验收标准；如同时满足稀疏 ADR 三条件，在 `docs/adr/` 同步立项。
- **推荐手段**：`/grill-me`（交互式需求压力测试）或直接结构化澄清。
- **出口产物**：`spec.md`（若适用则含 `docs/adr/NNNN-*.md`）。
- **放行门禁**：**用户明确拍板确认 `spec.md` 定稿**后，方可进入下一阶段。

#### 阶段 2：原型与契约（条件触发）
- **触发条件**：涉及 UI 且包含新的视觉样式、布局结构或交互决策。
- **跳过条件**：纯后端/CLI/脚本改动，或**仅复用既有设计体系组件与语义 token 且无新视觉决策**的 UI 改动，经确认可跳过本阶段，并在 `spec.md` 中注明「复用既有设计体系，无独立原型」。
- **推荐手段**：`figwright` 画原型；遇到原型工具无法复刻的浏览器特性（如 SVG `feTurbulence` 纸纹滤镜），走「浏览器实测 → `getComputedStyle`/canvas 换算 → 回写核对」提取真实值。
- **出口产物**：定稿原型 + `contract.md`（实现契约）。
- **放行门禁**：**用户明确拍板确认原型与 `contract.md` 定稿**后，方可进入阶段 3。

#### 阶段 3：切片与实现
- **3a 切片与上下文包**：
  - 将已定稿的 `spec.md` 与 `contract.md` 拆解为 `tasks.md`，每条 task 写明范围与独立验收标准（单次小改动可只列 1–2 条，保持同构）。
  - 派发给实现会话或子 agent 时，固定组装**上下文包**：`spec.md` 相关节选 + `contract.md`（如有）+ 当前 task 验收标准 + 关联文件清单。
- **3b 编码与即时自验**：
  - 治理体系全程在场：遵守 `AGENTS.md`、消费既有组件/原语、`web/src` 改完立即跑 `node scripts/check-design.mjs`（含写时自查 hook）。
  - **设想出入处理**：实现中一旦发现代码现状、接口约束或实际渲染效果与 `spec.md` / `contract.md` 不符，**立即停下上报分歧点**，禁止自行脑补、绕过或私自改契约继续写。
  - **实现期即时自验**：对每个用户可见改动做局部实机自验（前端截图与 `getComputedStyle`、服务端起进程发请求等），并记录进 `verify.md`。
- **出口产物**：代码与测试改动 + `verify.md`（实现自验段）。
- **放行门禁**：`tasks.md` 全部完成、局部自验已记入 `verify.md`，方可进入阶段 4。

#### 阶段 4：验收
- **对象区分**：实现期自验测**局部正确性**；验收期测**整体与关联面**（跨模块联动、主题/材质/响应式覆盖、回归影响），两级不可互替。
- **执行动作**：
  1. 跑全量自动化门禁：`npm run check`、`npm test`（以及构建产物验证 `npm run build`）。
  2. 执行端到端实机走查（前端浏览器多态走查、真实服务端接口、桌面壳或真宿主脚本；无法实测的明确记为「未实测 + 原因」）。若改动涉响应式布局或折叠/显隐动效，走查须额外覆盖**双视口/双容器宽度**（宽桌面 + 窄面板 `@container`）以及在 **`soft` 慢档下采样过渡中帧**（核对展开与收起均有连续中间高度/位移、收起终点零多余留白）。
- **出口产物**：补全 `verify.md` 中的门禁结果、实机证据与验收结论。
- **验收失败回路（按缺陷类型分流）**：

| 缺陷类型 | 回路 |
| --- | --- |
| 实现不符 `spec.md` / `contract.md` | 回阶段 3（附具体违例点修复并补验） |
| `spec.md` / `contract.md` 本身有误，或发生设想出入 | 回阶段 1 / 阶段 2，**先修订上游产物并经拍板**后再回阶段 3 |
| 验收发现未覆盖边界场景 | 补进 `spec.md` / `contract.md` / `tasks.md` 后回阶段 3 |

- **Git 提交门禁**：验收全绿后向用户汇报结论与变更范围；**经用户确认后再执行 `git commit` 与 `git push`**（遵循 Conventional Commits，实现与对应测试同提交）。

#### 阶段 5：CI
- `git push` 触发 `.github/workflows/compatibility.yml`，在 Ubuntu / macOS / Windows 三平台执行 `check + build + test`。
- 若 CI 失败，按失败类型回到阶段 3 补平台中性实现与测试，重新验收后推送。

#### 阶段 6：CD
- 推送与 `package.json` `version` 一致的 `vX.Y.Z` tag（或手动触发 `.github/workflows/release.yml`）构建三平台压缩包与 SHA-256 Artifacts。
- 边界：不做代码签名、公证与自动更新；Actions 流水线本身不无确认自动发布。CD 产物就绪并校验 SHA-256 后，须**经用户明确确认**才可执行 `gh release create` 创建 GitHub Release 并上传三平台压缩包与 `.sha256` 文件，同步更新 README 下载链接。

## 轻量档执行规范

- **路径**：`用户确认降档 → 实现（治理在场 + 局部即时自验）→ 验收（npm run check / npm test + 针对性实机）→ 用户确认后 commit / push`。
- **记录口径**：**不在 `docs/` 新建流程目录或文档文件**；直接在最终汇报中按 `AGENTS.md`「实测优先」要求陈述（改动说明、自动化门禁结果、实机怎么测/看到什么/未实测项与原因）。

## 过程产物规范（`docs/flows/`）

完整档产物统一落在 `docs/flows/<YYYY-MM-DD>-<topic>/`（位于 gitignored 的 `docs/` 过程区，不入库）。目录内按需沉淀以下 4 个轻量文件，保留最小骨架即可：

1. **`spec.md`（必填）**
   - 头部元信息（日期 / 主题 / 状态：`草稿 | 已定稿`）
   - 背景与目标 / 非目标
   - 已定决策与边界情况（涉 UI 但跳过原型时写明跳过依据）
   - 验收标准（可逐条核验）
2. **`contract.md`（进入阶段 2 时必填）**
   - 头部元信息（关联 `spec.md` / 原型参考 / 状态：`草稿 | 已定稿`）
   - 关键样式与 Token 契约（实测或换算后的明确数值/变量名）
   - 组件与原语复用映射（拟复用的 `ui/*` 原语 / `panel/*` 组件、动效契约槽位 `--component-*-duration`，或需新建原语的理由与接口签名）
   - 交互、状态与材质约束要点
3. **`tasks.md`（进入阶段 3 时必填）**
   - 切片列表：每条含 `Task ID`、`改动范围`、`上下文包索引`（引用的 spec/contract 章节与关联文件）、`独立验收标准`、`状态`
4. **`verify.md`（进入阶段 4 前必填）**
   - 自动化门禁结果（`npm run check` / `npm test` / `npm run build` 实际输出摘要）
   - 实现期局部自验记录 + 验收期端到端实机走查记录（路径、操作、观测结果/截图要点）
   - 未实测项与原因（如无则写“无”）

## 验证产物留存准则（过程验证 vs 长期回归资产）

为防止开发期临时脚本和单点测试长期堆积、污染 Agent 上下文与仓库维护成本，所有验证代码按下列规则分流：

1. **开发期一次性脚手架与探针**：不放进 `scripts/` 入库。需要编写临时探针、旁路验证或一次性压测脚本时，一律放当前流程目录 `docs/flows/<YYYY-MM-DD>-<topic>/scratch/`（或系统临时目录）；阶段 4 验收完成后随过程区忽略或按需清理。
2. **长期入库条件**（须同时满足）：能在 `npm run check` / `npm test` / CI 中无人工前置、确定性运行以拦截回归（或属于 `guide/development.md` 登记的现行主链路真宿主验收工具），且后续接口变更时值得同步维护。
3. **自动化测试收敛规则**：
   - 新增回归用例优先**并入所属模块现有的 `unit/`、`contract/` 或 `web/tests/` 测试文件**，不为单次缺陷修复或单个辅助函数另建 1–2 个用例的碎片文件；
   - `src/tests/internal/` 只钉住无法从公共契约观察到的底层不变式（数据库迁移、事务嵌套、特定写合并策略），迁移用例按主题集中维护，不按每个 schema 版本拆散文件；
   - `src/tests/process/` 只放确需真实进程/端口握手的链路。
4. **存量清理纪律**：开发过程中如发现已被正式实现和契约测试替代的历史过程脚本（如早期探针），在确认无引用后随任务或单独清理，不任其继续充当后续 Agent 的误导样本。

## 产物落点与稀疏 ADR 规则

- **统一文档目录与白名单入库**：`docs/` 整体默认不入库（`.gitignore` 的 `docs/*`），其中持久文档资产通过在 `.gitignore` 显式声明白名单入库（如 `!docs/adr/**`、`!docs/DESIGN.md`、`!docs/dev-flow-spec.md`）；开发过程产物（`docs/flows/` 下的 `spec.md` / `contract.md` / `tasks.md` / `verify.md`）不入库。
- **稀疏 ADR 触发条件**（须同时满足三条才建，建在 `docs/adr/`，避免全量流水账）：
  1. 难逆转的架构/协议/数据边界决定；
  2. 缺少上下文会让后来者困惑或误改；
  3. 经过真实权衡取舍的结果。
