# 开发流程 Spec（本仓库的开发工作流定义）

> 本文档是「我们如何开发」这套流程的唯一事实源，由 2026-11-21 流程设计会与 2026-11-24 去档位化及测试体系减负重构裁决构成。
> 修订规则：流程裁决变更时先改这里，再同步 `AGENTS.md` 的「开发工作流」与「工具、门禁与测试」段。
> 作用域：本仓库的前端、后端与桌面壳自身开发。不涉及 `agent-team` 框架的业务能力（成员/派单/协作）——流程的执行者是用户与 agent 主控会话，与框架业务解耦。

## 目标

给「需求对齐 → [按需]原型与契约 → 实现与自验 → 验收与提交 → CI → CD」全周期定义清晰的触发条件、人机拍板点、失败回路与轻量化验证机制：大改动严谨可追溯、小需求无繁文缛节、本地快反馈、远端 CI 集中兜底。

## 非目标

- 不定义 `agent-team` 框架自身的协作功能（派单、成员会话、内置模板）——那是被开发的业务。
- 不做代码签名、公证、自动更新（桌面端既定约束，CD 不含自动上线）。
- 不设“完整档 / 轻量档”及“降档审批权”——按客观变更条件与任务规模自适配，不做机械贴标签。
- 不为判断型规则（如实机验证尺度）建静态检查；也不在本地构造复杂的测试路由编排框架。

## 术语与工具边界

| 术语 | 定义 |
| --- | --- |
| `spec.md` | 需求对齐产物：目标 / 非目标 / 已定决策 / 边界情况 / 验收标准（按触发条件落盘） |
| `contract.md` | 原型阶段出口产物（实现契约）：关键样式与 token 值、组件复用/新建清单、状态与交互验收要点（仅进入原型阶段时产出） |
| `tasks.md` | 实现前切片清单：多切片/跨模块/派发子 Agent 时将 spec/契约拆为独立切片与验收标准 |
| 上下文包 | 派发给实现子 Agent 时的固定输入：`spec.md` 相关节选 + `contract.md`（如有）+ 当前 task 验收标准 + 关联文件清单 |
| `verify.md` | 验证记录：当本次任务已建 `docs/flows/` 目录时，记录静态检查、定向测试与实机走查结论 |
| 设想出入 | 实现期发现现状代码、契约或效果与既定设想不符的一等事件：**立即停下上报分歧点，禁止自行脑补** |

> **跨宿主工具原则**：流程规定的是**阶段职责与触发条件**，具体工具（如 `grill-with-docs` / `figwright`）为推荐手段而非硬绑定；不同宿主按当前可用工具完成对应职责即可。

## 单一自适配流程模型

所有任务共享同一条主线，不区分档位、不走“降档审批”；仅在命中对应客观条件时触发重产物与拍板门禁：

```
1 需求对齐        命中 3 条红线 → 写 spec.md（+ 稀疏 ADR）          [门禁：用户拍板]
                 无歧义小改    → 简短对齐或直接进阶段 3
2 原型与契约      [默认跳过] 仅涉新 UI 视觉/布局/交互决策时触发      [门禁：用户拍板]
3 实现与自验      多切片拆 tasks.md → 写时 hook 在场 + 定向单测/自验
4 验收与提交      改动端静态检查 + 定向测试 + 分级实机（L0/L1/L2）   [门禁：用户确认 commit/push]
5 CI             推送触发 compatibility.yml（三平台全量 check + build + test + desktop-smoke）
6 CD             tag push 构建三平台产物；校验 SHA-256 后经用户确认创建 GitHub Release
```

### 阶段细则与触发条件

#### 阶段 1：需求对齐
- **何时必须先写 `spec.md` 并经用户拍板**（满足任一条即触发）：
  1. 新增或改变用户可见的功能、交互或外部接口契约（HTTP / MCP / RPC / CLI / 桌面壳）；
  2. 涉及架构、数据模型/表结构、新设计 token 或新组件原语等权衡取舍；
  3. 需求本身存在多种合理理解，或需要跨多模块协同。
- **何时可直接进入实现**：不满足以上三条的无歧义局部改动（纯文档、根因唯一的缺陷修复、改法已明确的样式/文案/参数微调）直接动手，不强建 `docs/flows/` 目录；一旦动手中发现范围膨胀或冒出取舍，立即按「设想出入」停下补对齐。
- **推荐手段**：`/grill-with-docs`（交互式需求压力测试）或直接结构化澄清；如同时满足稀疏 ADR 三条件，在 `docs/adr/` 同步立项。

#### 阶段 2：原型与契约（默认跳过，按需触发）
- **触发条件**：仅当改动涉及 UI 且包含**新的视觉样式、布局结构或交互决策**，或用户明确要求画原型时进入。
- **默认跳过**：纯后端/CLI/脚本/文档改动，或**仅复用既有设计体系组件与语义 token 且无新视觉决策**的 UI 改动，Agent **直接跳过**（若建了 `spec.md`，在其中一笔注明即可，不再为“跳过原型”额外请示确认）。
- **推荐手段**：`figwright` 画原型；遇到原型工具无法复刻的浏览器特性（如 SVG `feTurbulence` 纸纹滤镜），走「浏览器实测 → `getComputedStyle`/canvas 换算 → 回写核对」提取真实值。
- **出口产物与门禁**：定稿原型 + `contract.md`，**经用户明确拍板确认**后进入阶段 3。

#### 阶段 3：实现与自验
- **切片与上下文包（按需）**：多切片推进、跨模块重构或派发子 Agent 时，在流程目录拆 `tasks.md` 并组装上下文包；单文件/单点改动直接省略 `tasks.md`。
- **编码与写时护栏**：
  - 遵守 `AGENTS.md` 硬红线、复用既有组件/原语；
  - 写时瞬时 hook（`scripts/check-design-hook.mjs`，~0.2s）在编辑 `web/` 文件时自动拦截设计令牌与前后端隔离违规，违例当场修复。
  - **设想出入处理**：实现中一旦发现代码现状、接口约束或渲染效果与 `spec.md` / `contract.md` / 既有约定不符，**立即停下上报分歧点**，禁止自行脑补或绕过。
- **开发期自验**：每改完一个逻辑单元，只跑**当前改动直接对应的定向测试文件**（如单个 `*.test.mjs` / `*.test.ts`）与必要的局部实机确认，不在开发迭代中反复跑全量测试。

#### 阶段 4：验收与提交
- **本地门禁（极简定向，不替 CI 跑全量回归）**：
  1. **静态检查（按改动端执行）**：
     - 纯文档改动：`npm run check:docs`（改发版版本/README 链接时补 `npm run check:version`）；
     - 触及前端（`web/`）：`npm run check:web`（`check-design` + `check-layering` + `vue-tsc` + `eslint web/src`）；
     - 触及后端/脚本/桌面壳（`src/`、`scripts/`、`electron/`）：`npm run check:backend`（语法/导入 + `tsc` + `eslint`）；
     - 跨端或改构建/配置（`package.json`、`eslint`、`tsconfig`）：`npm run check`（必要时 `npm run build`）。
  2. **自动化测试（本地只跑本次直接相关文件）**：
     - 纯文档改动：**0 个测试**；
     - 代码改动：只运行与本次新功能或缺陷直接对应的测试文件（如 `node --disable-warning=ExperimentalWarning --test src/tests/core/<module>.test.mjs` 或 `npx vitest run --config web/vite.config.ts web/tests/<path>.test.ts`）；
     - 历史全量回归与跨平台测试统一交由推送后的 CI 集中兜底（仅发版打 tag 前、大规模测试体系调整或用户主动要求时本地跑全量 `npm test`）。
- **实机验证与汇报（按风险分三级）**：

| 级别 | 适用改动 | 实机要求 | 汇报要求 |
| --- | --- | --- | --- |
| **L0 非运行态** | 纯文档、注释、纯测试调整 | 免实机 | 一句话汇报实际跑过的静态检查/定向测试即可，免三段式占位文案 |
| **L1 局部小改** | 单点样式/文案、局部 bug 修复、单一接口微调 | 对改动点做最小定向实机确认（看对应界面截图或发一次对应请求） | 简述静态检查、定向测试与改动点观测事实 |
| **L2 功能级 / 高风险** | 新功能、复杂交互/响应式/动效改造、宿主生命周期、桌面壳 | 完整端到端实机走查（涉响应式或折叠动效时覆盖宽/窄双视口与 `soft` 档过渡中帧） | 完整三段式汇报（门禁结果 / 实机证据 / 未实测项与原因）；已建流程目录时同步写入 `verify.md` |

- **验收失败回路**：
  - 实现不符 `spec.md` / `contract.md` → 回阶段 3 修复并补验；
  - `spec.md` / `contract.md` 本身有误或发生设想出入 → 回阶段 1 / 阶段 2 先修订并拍板后再改代码；
  - 发现未覆盖边界场景 → 补进上游文档后回阶段 3。
- **Git 提交门禁**：验收通过后汇报结论与变更范围；**经用户确认后再执行 `git commit` 与 `git push`**（Conventional Commits）。

#### 阶段 5：CI（集中全量回归兜底）
- `git push` 触发 `.github/workflows/compatibility.yml`，在 Ubuntu / macOS / Windows 三平台集中执行全量 `npm run check`、`npm run build`、`node scripts/build-release.mjs --dry-run`、`npm test` 以及 macOS `desktop-smoke`。
- 若 CI 暴露历史回归或跨平台差异，回到阶段 3 补平台中性实现与回归用例，重新推送。

#### 阶段 6：CD
- 推送与 `package.json` `version` 一致的 `vX.Y.Z` tag（或手动触发 `.github/workflows/release.yml`）构建三平台压缩包与 SHA-256 Artifacts。
- 边界：不做代码签名、公证与自动更新；Actions 流水线本身不无人确认自动发布。CD 产物就绪并校验 SHA-256 后，须**经用户明确确认**才可执行 `gh release create` 创建 GitHub Release 并上传三平台压缩包与 `.sha256` 文件，同步更新 README 下载链接。

## 高杠杆测试体系准则（详见 `docs/adr/0016-lightweight-guardrail-testing.md`）

本仓库自动化测试的唯一目的是**约束 Agent 不改坏核心逻辑与外部契约、防止历史缺陷复发**，严控测试体量与维护噪音：

1. **什么必须写/改测试**：
   - 后端：SQLite 逐级迁移与保留策略、聚合写边界不变式、消息投递/恢复/并发状态机、对外公开契约（HTTP / MCP / RPC / 权限与能力路由）、少量核心进程冒烟；
   - 前端：纯 TypeScript 业务逻辑、状态机、SSE 流式归约、主题解析与插件契约；
   - 缺陷回归：修过一次的真实逻辑 bug，在所属模块既有测试文件中补一条回归用例防复发。
2. **什么明确不要求写测试**：
   - 纯样式/布局微调、纯文案、纯文档；
   - Vue 组件 DOM 挂载（`mount()`）、SSR HTML 字符串渲染、CSS 类名与布局壳测试（UI 交由 `vue-tsc` + `check-design.mjs` + 实机浏览器兜底）。
3. **测试目录结构（精简两层）**：
   - `src/tests/core/`：快速核心与契约测试（内存 / 临时 SQLite），日常按单文件定向运行；
   - `src/tests/smoke/`：极少数必须起真实子进程或端口的关键端到端冒烟（默认由 CI 兜底）；
   - `src/tests/support/`：后端共用夹具；
   - `web/tests/`：按 `web/src/` 结构组织的纯逻辑 Vitest 单测，统一经 `@/` 引用源码。
4. **留存铁律**：
   - 开发期一次性探针/脚手架放当前流程目录 `docs/flows/<YYYY-MM-DD>-<topic>/scratch/`（或系统临时目录），绝不放进 `scripts/` 入库；
   - 新用例优先并入所属模块既有测试文件，不建 1–2 用例碎片文件。

## 过程产物规范（`docs/flows/`）

当任务触发 `spec.md` 时，过程产物统一落在 `docs/flows/<YYYY-MM-DD>-<topic>/`（位于 gitignored 的 `docs/` 过程区，不入库），仅按需建以下轻量文件：

1. **`spec.md`（命中阶段 1 红线时必填）**：日期 / 主题 / 状态（`草稿 | 已定稿`）、背景与目标 / 非目标、已定决策与边界、可逐条核验的验收标准。
2. **`contract.md`（仅进入阶段 2 原型时必填）**：关联 `spec.md` / 原型参考 / 状态、关键样式与 Token 契约、组件与原语复用映射、交互/状态/材质约束。
3. **`tasks.md`（仅多切片或派发子 Agent 时必填）**：`Task ID`、`改动范围`、`上下文包索引`、`独立验收标准`、`状态`。
4. **`verify.md`（已建流程目录且进入 L2 验收时必填）**：实际执行的门禁摘要、端到端实机走查证据、未实测项与原因。

## 产物落点与稀疏 ADR 规则

- **统一文档目录与白名单入库**：`docs/` 整体默认不入库（`.gitignore` 的 `docs/*`），持久文档资产通过 `.gitignore` 白名单入库（如 `!docs/adr/**`、`!docs/DESIGN.md`、`!docs/dev-flow-spec.md`）；`docs/flows/` 不入库。
- **稀疏 ADR 触发条件**（须同时满足三条才建，建在 `docs/adr/`）：
  1. 难逆转的架构/协议/数据边界决定；
  2. 缺少上下文会让后来者困惑或误改；
  3. 经过真实权衡取舍的结果。
