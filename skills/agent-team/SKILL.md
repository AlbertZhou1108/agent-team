# Agent Team

依据已确认的目标契约和真实团队记录推进协作。会话 Agent 按需主动查询团队；不依赖团队消息自动推送到用户私聊，也不持续轮询。

## 先确认入口

先从当前身份、输入和实际暴露的工具确认上下文，不凭用户称呼推断权限。

| 上下文 | 当前职责 | 按需读取 |
| --- | --- | --- |
| 外部会话，尚未连接团队 | 定位项目和数据目录，帮助启动或连接；未读取前不声称知道群状态 | [用户指南](references/user-guide.md) |
| 建群准备 preparation | 整理契约与普通角色模型计划，等待用户确认 | [主 Agent 流程](references/lead-workflow.md)的建群部分 |
| 用户私聊 private | 主动查询团队、解释事实，指引用户使用可信操作入口 | [会话 Agent](references/conversation-agent.md) |
| 主 Agent coordination | 管理工作项、派发、处理汇报、审查、接受与收尾 | [主 Agent 流程](references/lead-workflow.md) |
| 普通成员 pair | 按工作项执行、协作或独立审查，并用群消息汇报 | [成员流程](references/member-workflow.md) |
| 入群自述 profile | 用 profile_set 只写本人真实能力，然后结束回合 | 无需加载其他流程 |

身份和上下文共同决定可用工具。同一主成员的 private 与 coordination 不共享完整会话上下文；private 不能直接派工或写工作项。工具不可用时说明正确入口，不读取内部凭据、直接改库或切换身份绕过限制。

## 核心流程

1. 确认群、工作区、当前目标版本、有效契约和执行阶段。查询问题先读取事实；执行请求先核对授权与当前上下文。
2. 将目标组织为可整体接受的成果，明确参与职责、实际权限、审查要求和并行修改范围。
3. 通过 send 派发与汇报，按需 read 补上下文。根据目标缺口选择继续、补充、返工、接受、阻塞或收尾，无固定讨论轮数。
4. 使用确定成果版本、真实贡献消息和必要独立审查作出接受判断。
5. 用已接受成果覆盖完成条件，处理剩余正式消息，提交最终交付并核对实际收尾状态。

## 必须保留的边界

- 用户私聊不自动共享。需要团队执行的指令走明确共享入口；用户批准绑定具体契约或请求，Agent 不代替用户批准。
- 契约是权限上限；工作项及回合继续收窄。主 Agent 普通协调仅沟通，亲自执行也需列为执行参与者；审查者最多只读。文件策略不代表全面网络隔离。
- 等待团队新消息时结束当前回合，由框架再次唤醒；不调用宿主原生子 Agent、阻塞 wait 或另外建立团队调度。
- send 返回编号只证明消息已记录；成员汇报、独立审查、主 Agent 接受和目标完成分别核实。宿主最终文本不会自动成为群汇报。
- 共享目录没有文件锁。修改前明确归属与交接；成果更新后重新核对对应版本的审查。
- closed 表示当前目标结束，群仍可交流。后续项目执行通过 next_goal_request 提交完整新契约，用户批准后才开始；历史工作项与交付保持只读。

## 按问题补充参考

- 用户询问进度、聊天、决定依据或是否完成：读[会话 Agent](references/conversation-agent.md)。
- 启动、恢复、共享指令、确认或成员操作：读[用户指南](references/user-guide.md)。
- 版本冲突、发送失败、重复输入、运行不确定或无法完成：读[恢复指南](references/recovery.md)。

工具逻辑名如 send、read 在宿主中可能带 agent_team_ 前缀；使用当前实际暴露的名称和参数 schema。此 Skill 安装不会自动建立团队连接，也不保证受限团队宿主会加载它。
